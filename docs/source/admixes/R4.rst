Building
--------

The `R4-admix repository <https://github.com/RCIC-UCI-Public/R4-admix/>`_ 
is used to build multiple versions of R4 and Rstido. 
R4 is relatively complex build and requires local changes to its Makefile to
accomplish multiple builds.

Here is the full process for rebuilding R4 and its associated modules present in the repo:

.. parsed-literal::
   :command:`git clone https://github.com/RCIC-UCI-Public/R4-admix.git
   cd R4-admix
   make buildall-parallel &> buildall.log &`

.. warning:: 
   This process will install RPMs as it builds. You should do this on a 'disposable' build system.

When building packages for R modules we use native R tools 
and modules such as command ``R CMD INSTALL`` or **miniCRAN** module logic to
get packages recursive dependency resolution.

The following sections provide detailed explanation about repo files,
build process, and adding new modules step-by-step.

In yamlspecs/
~~~~~~~~~~~~~

Standard files
^^^^^^^^^^^^^^

When building R4 modules we not only need to build different versions of
R4 itself but also need to have different modules that were requested by the users
in order to support different types of applications.
Such modules trigger its own chain of dependent R4 modules that need to be installed. 

We create a set of modules to install for each version of R. 
While we try to keep the sets contents the same, sometimes it is not possible
as the specific modules dependencies change.
There is a specific order when in the set a module can be built. Some needs to
be build and installed before others can be compiled. Others need their
dependencies only during the module install.
We have to handle such dependencies carefully so that we do not
create circular references during the build.

``packages.yaml`` (required)
  Yaml format, describes specifics of this admix build.

  .. literalinclude:: files/R4-admix-packages.yaml
     :language: yaml

  Most of the variables in this file are standard
  (:yvars:`site`, :yvars:`system`, :yvars:`bootstrap`, :yvars:`build`, :yvars:`manifest`, :yvars:`sets`).
  There are a few new variables in this file that allow us
  to  define a list of system RPMS to be added only when building for a specific OS.

  - :yvars:`bootstrap` - lists two separate bootstrap variables. The
    :yvars:`bootstrap0` is basically defined via :yvars:`basebuild`: R, R-module,
    rstudio, rstudio-module plus a couple other basic R modules. The
    :yvars:`bootstrap0` can be redefined for eash set. 
    The :yvars:`bootstrap1` is defined from the desired modules. 

  - :yvars:`!ifeq "{{site.os_release}},7,icu-devel,libicu-devel"` was
    evaluated to *icu-devel* on OS 7 and to *libicu-devel* on any later OS.
    This gives us flexibility via this logic to use a single line or file
    instead of rewriting them for a different OS.

  - :yvars:`!eval "'libgit2-devel' if {{site.os_release}} == 8 else ''"`
    is similar to :yvars:`!ifeq` statement. Here on OS 8 *libgit2-devel* RPM will be
    added on the build host before any packages are built.

  - :yvars:`bootstrap` and :yvars:`build` - empty, no builds in the base
    set. All builds are in the specific sets.

  - :yvars:`sets` - lists the sets to be built. Here for a set name we use a short hand
    notation of a R version (452 for R 4.5.2, etc).
  - :yvars:`parallel` -  says build all 6 sets in parallel.

Makefile
^^^^^^^^

The ``Makefile`` is specific to R4-admix.

* It includes a generic template via :yvars:`include $(YAML2RPM_HOME)/sys/Makefile` directive
  that provides defaults used for building RPMs;
* Adds targets to override defaults. For example :yvars:`thaw`, :yvars:`copyset`, :yvars:`thawyamls`, :yvars:`thawsources`.
* Adds specific targets used for a :ref:`creation of additional modules <R4_admix_add_modules>`.
  For example :yvars:`prep`, :yvars:`builddeps.yaml`, :yvars:`buildorder`,
  :yvars:`outversions.yaml`, :yvars:`freeze`, :yvars:`cleanset`. 

When executing any target defined in ``Makefile`` **always give it a set name
as an argument**, for example:

  .. parsed-literal::
     :command:`make bootstrap SET=442`
     :command:`make manifest SET=452`

``common.yaml``
  A template that provides a set of variables for build that is used for
  every R module: 

  .. literalinclude:: files/R4-admix-common.yaml
     :language: yaml

  Here we define all the common varialbes that are reused for every package
  and others that can be overwritten (notably :yvars:`requires`) in a given package yaml file when needed.

| ``rstudio.yaml`` 
| ``rstudio-module.yaml``
|   Used to build *Rstudio* and its module.

| ``abseil-cpp.yaml``
| ``abseil-cpp-module.yaml``
|   Used to build *abseil-cpp* and its module, they are prerequisites for *s2* R module.

| ``GenomeInfoDbData.yaml``
| ``seurat-data.yaml``
| ``tmvnsim.yaml``
|   Used to build a few specific R module packages.

``hdf5r.patch``
  Used to patch specific versions of *hdf5* distribution series *1*. Reference to a
  patch is in the respective  ``hdf5r.yaml`` files in *freeze* directories.
  The patch updates *configure.ac* and *m4* files of the source distro.

``hdf5r-1.3.12.patch``
  Used to patch specific versions of *hdf5* distribution series *2*. Reference to a
  patch is in the respective  ``hdf5r.yaml`` files in *freeze* directories.
  This a patch for *hdf5r* adds compiler flags to downgrade errors to
  warnings. This comes from using gcc compiler series v.15 which has much
  stricter checking.

``NAME.yaml.append``
  Any files with this naming schema are created by hand based on what a
  specific module yaml files needs to include for a successful build.
  While we generate nearly all module yaml files automatically, a few have
  specific build needs that are not possible to address programmatically
  just via using CPAN tools, so they are enabled via creating an append file. 
  The append files are created individually based on specific module
  compilation, patching needs or updates to provides/requires.

  For example, an auto-generated file for *hdf5r* module looks like this:

  .. code-block:: yaml 

     !include common.yaml
     ---
     - package: R module hdf5r
       name: hdf5r
       rpkgname: hdf5r
       version: "{{versions.hdf5r}}"
       baseurl: https://cran.r-project.org/src/contrib
       src_tarball: "{{rpkgname}}_{{version}}.{{extension}}"
       vendor_source: "{{baseurl}}/{{rpkgname}}_{{version}}.{{extension}}"
       requires:
         - R_{{Rversion}}
         - R_{{Rversion}}-R6
         - R_{{Rversion}}-bit64
         - R_{{Rversion}}-bit

  However this  does not have patching info, or compiler directives update
  info. Those are coming from ``hdf5r.yaml.append``:

  .. literalinclude:: files/R4-admix-hdf5r.yaml.append
     :language: yaml

  The resulting ``hdf5r.yaml`` file is a concatenation of the two files above
  and can be found in *freeze* directories.

``modules.bootstrap``
  Listing of a few packages for **R** and **rstudio** that are built initially 
  in the :yvars:`bootstrap0` phase. We need to reference this listing a few
  times when building packages for different sets, using a simple file simplifies the tracking.

``modules.desired``
  Listing of R modules (names one per line)  that we want to install. This is a base template that
  was used initially for building modules for each set. Once a set is built
  a (sometimes modified per final build outcome) file is saved in each *freeze* directory.

Set specific
^^^^^^^^^^^^

The set files and corresponding versions files enable us to create multiple
versions of desired modules for multiple versions of R:

  .. table::
     :class: noscroll-table

     +---------+---------------+-------------------+------------+
     | R       | Set           |  Versions         | Freeze     |
     | version | file          |  file             | directory  |
     +---------+---------------+-------------------+------------+
     | 4.0.4   | set-404.yaml  | versions-404.yaml | freeze-404 |
     |         |               |                   |            |
     | 4.1.2   | set-412.yaml  | versions-412.yaml | freeze-412 |
     |         |               |                   |            |
     | 4.2.2   | set-422.yaml  | versions-422.yaml | freeze-422 |
     |         |               |                   |            |
     | 4.3.3   | set-433.yaml  | versions-433.yaml | freeze-433 |
     |         |               |                   |            |
     | 4.4.2   | set-442.yaml  | versions-442.yaml | freeze-442 |
     |         |               |                   |            |
     | 4.5.2   | set-452.yaml  | versions-452.yaml | freeze-452 |
     +---------+---------------+-------------------+------------+

When we create specific R modules for a given set we try to keep the listing
consistent but this is not always possible. A new version of a given module
may have different prerequisites for a different set and this results in a
different content of the yaml file for a specific module or a slightly
different set of files. This is why after we create the yaml files for sets 
of modules we save them in *freeze* directories, one directory per set so that there is
no conflict.

Any individual set can be built separately, for example:

   .. parsed-literal::
      :command:`make buildall SET=452`

Sets define individual packages for each R version.
For example ``set-452.yaml`` (partial listing):

  .. code-block:: yaml

     !include packages.yaml
     ---
     versions: versions-452.yaml
     bootstrap0:
       - R
       - R-module
       - GenomeInfoDbData
       - rstudio
       - rstudio-module
       - abseil-cpp
       - abseil-cpp-module
     # contents from buildorder
     bootstrap1:
       - BayesCombo
       - cli
       - magrittr
       - Rcpp
       - rlang
       ...

The :yvars:`bootstrap0` entries are basic packages for this set and they must be built
and immediately installed in the listed order. The entries in :yvars:`bootstrap1` were created via a special process
(:ref:`see below <R4_admix_add_modules>`) and they too must be built and installed in the listed order.
Note, the listed order in this entry is not necessarily unique.

The versions files define each package version and any additional variables
needed for building. For example, ``versions-452.yaml`` (partial listing):

  .. code-block:: yaml

     !include versions.yaml
     !include site97.yaml
     ---
     R: "4.5.2"
     Rmajor: "4"
     Rminor: "5"
     tarsources: "20260130"
     addonsources:
     rstudio: "2026.01.0.392"
     rstudio_dist: "2026.01.0-392"
     rstudio_os: "rhel9"
     rstudio_site: "electron"
     rstudio_layout: "new"
     abseil_cpp: "20250814.0"
     OpenBLAS: "0.3.31"
     gdal: "3.12.1"
     geos: "3.14.1"
     proj: "9.7.1"
     fftw: "3.3.10"
     glpk: "5.0"
     hdf5: "2.0.0"
     libgit2: "1.8.5"
     GenomeInfoDbData: "1.2.15"
     seurat_data: "0.2.1"
     ## from outversions.yaml
     BayesCombo: "1.0"
     cli: "3.6.5"
     magrittr: "2.0.4"
     Rcpp: "1.1.1"
     ...
     robustbase_subversion: "6"
     robustbase: "0.99"

Variables :yvars:`gdal`, :yvars:`geos`, and similar provide versions of the
dependent software packages (outside of R4-admix) that are needed for
compilation of some R modules. 

Any variable with :yvars:`_subversion` shows a specific portion of the
package version.  Using it allows us to keep a single :yvars:`vendor_source`
line for multiple versions of each package. There is no single naming schema
how developers name their packages or create distro files. 

.. _R4_admix_scripts:

Scripts
^^^^^^^

There are a few scripts that we created to enable specific tasks.
See the scripts files contents in `R4-admix repository <https://github.com/RCIC-UCI-Public/R4-admix/>`_.
All the scripts are specific to R4-admix.

| ``filter-requires-RPostgreSQL.sh``
| ``filter-requires-rstudio.sh``
| ``filter-requires-styler.sh``
|   These bash scripts are used to parse requires during the ``rpmbuild`` run for
    named packages. They remove some third party hard-coded erroneous
    requirements (such as references to /usr/local or system supplied libraries
    at a specific version that does not exist).
    As a result only OS-installed libraries names are left in requires and they satisfy the package needs.

``deps.R``
  This R script reads the files ``modules.desired``  and ``modules.bootstrap`` to generate a single yaml file
  ``builddeps.yaml`` of all R packages dependencies for the desired modules list. It uses the *miniCRAN*
  R module, which does recursive dependency resolution.
  The ``builddeps.yaml`` file can then be processed to determine the build/bootstrap order
  of R RPMs, it can also be used to place dependencies in R module RPMs.

``depend.py``
  This Python script is called from the ``Makefile`` when there is a need to create some new modules
  for the existing groups or add a new group of modules for a new set. This script was used to create 
  all yaml files for the modules in *freeze* directories.

  The script will take as an input created modules dependency ``builddeps.yaml`` and
  bootstrap list  of modules from ``modules.bootstrap``  and create R modules
  yaml files, ``buildorder`` and ``outversions.yaml`` files.

``downloadpkg.py``
  This Python script reads created ``builddeps.yaml`` and downloads listed
  packages sources distributions for a specific set. All downloaded files will
  be in the ``sources/`` subdirectory directory  at the top repo level.

For details how to use these scripts when adding new modules see the following section. 

.. _R4_admix_add_modules:

Add new modules
---------------

The steps below outline how one can add new R modules.
There are two scenarios.

Add to the existing R set
~~~~~~~~~~~~~~~~~~~~~~~~~

Lets look at the first scenario where we add 2 new modules
to the existing set for R 4.5.2.

1. Create ``modules.desired`` file with the following contents 
   (save original as ``modules.desired.save``).

   .. code-block:: text

      mclust
      scoringRules

#. Run the command to generate dependencies yaml file
   and indicate the set (important!). Your output should be similar  to:

   .. parsed-literal::
      :command:`make builddeps.yaml SET=452`
      ( module load R/4.5.2; \
        cat deps.R | R --slave > builddeps.yaml  )
      PKG mclust
      PKG scoringRules
      PKG Rcpp
      PKG MASS
      PKG knitr
      PKG RcppArmadillo
      PKG evaluate
      PKG highr
      PKG xfun
      PKG yaml
   
   The generated file ``builddeps.yaml`` contains definitions and dependencies
   among the 10 listed  in the output packages that will be needed to install 2
   packages we defined in ``modules.deired`` (2 desired plus 8 required as dependencies
   as was found by :command:`deps.R`). 

   Check these PKG names in the ``set-452.yaml``. All but two new modules names  are
   present. These means we already have yaml files and source distibutions for the
   modules from the previous execution of initialy building set for this R version.

#. The next step is to create ``buildorder`` file: 

   .. parsed-literal::
      :command:`make buildorder SET=452`
      ./depend.py > buildorder
      INFO: Not writing yaml file for system package MASS

   Note, the *INFO* line.  This means *MASS* is installed as a part of the
   R RPM, no need to create an extra package for it. IN the following steps 
   *MASS* is not considered anymore. 

   A few files are generated:

     - ``buildorder`` lists in what order the build of 9 packages
       should be made in relation to each other.
     - ``outversions.yaml`` lists the versions for the 9 packages.
     -  9 yaml files for respective 9 packages. 

#. Check generated files. 

   In general, once we release a specific R set and install it on the cluster, we do not change modules
   packages versions in it so that we provide a consistent environment to the
   users who are already using this R version. 

   We are now adding new modules to the previously built set of modules. Some dependencies
   may have already been built for the set. We have to check what they are and if they changed
   and resolve discrepancies or any issues. This is a very important and a bit involved step.

   ``buildorder``
     Check ``buildorder`` entries vs. ``set-452.yaml`` entries. All names but *mclust* and
     *scoringRules* are already present in the set file.  The ``buildorder`` contents are:

       .. code-block:: text

          mclust
          Rcpp
          evaluate
          xfun
          highr
          yaml
          knitr
          RcppArmadillo
          scoringRules

     This is the build order if we were to build just these packages from ground zero.
     The already existing ``set-452.yaml`` has many more packages and thus the order
     in how already existing packages listed there can be different. 

     Regardless of the difference, the important rule holds: all packages that
     are needed by any given package in the set file come in the listing before
     that package. Here we really need to check only 2 new packages yaml files
     and what dependencies they require.

   ``outversions.yaml``
     Check ``outversions.yaml`` entries vs ``versions-452.yaml`` entries. New
     entries will be for *mclust* and *scoringRules*. But some packages that
     were already installed have newer versions in ``outversions.yaml``
     (comments are added for readability, they don't exist in the actual file):

       .. code-block:: text

          mclust: "6.1.2"                # new
          Rcpp_subversion: "1.1"         # new
          Rcpp: "1.1.1"                  
          evaluate: "1.0.5"
          xfun: "0.57"                   # was 0.56
          highr: "0.12"                  # was 0.11
          yaml: "2.3.12"
          knitr: "1.51"
          RcppArmadillo_subversion: "1"
          RcppArmadillo: "15.2.6"        # was 15.2.3
          scoringRules: "1.1.3"          # new

     The two new modules version are expected (we had none before). But *Rcpp_subversion*
     did not exist in the versions file for this set. This means that an
     actual version for this package distribution source is new now. Was *1.1.1* and currently *1.1.1-1.1*.
     Versions for *xfun*, *highr* and *RcppArmadillo* got updated (compare to what we
     initially created for this set).

   ``mclust.yaml``
     This is a first new package file.  It does not depend on any other package,
     and no other package requires this package. File contents:

       .. literalinclude:: files/R4-admix-mclust.yaml
          :language: yaml

   ``scoringRules.yaml``
     This is a second new package file. It depends  on the rest of the packages listed in
     the ``buildorder`` but no other packages depend on this new package.

     File content:
       .. literalinclude:: files/R4-admix-scoringRules.yaml
          :language: yaml

   The rest of generated NAME.yaml
      Check the generated package yaml files against already present
      in ``freeze-452/`` directory. For example:

        .. parsed-literal::
           :command:`PKG="Rcpp knitr RcppArmadillo evaluate highr xfun yaml"
           for i in $PKG; do echo "PKG=$i"; diff $i.yaml freeze-452/$i.yaml; done`
           PKG=Rcpp
           7,9c7
           <   sversion: "{{versions.Rcpp}}"
           <   subversion: "{{versions.Rcpp_subversion}}"
           <   version: "{{sversion}}.{{subversion}}"
           ---
           >   version: "{{versions.Rcpp}}"
           11,14c9,10
           <   src_tarball: "{{rpkgname}}_{{sversion}}-{{subversion}}.{{extension}}"
           <   vendor_source: "{{baseurl}}/{{rpkgname}}_{{sversion}}-{{subversion}}.{{extension}}"
           <   description: >
           <     {{rpkgname}} version {{sversion}}-{{subversion}} for R version {{Rversion}}.
           ---
           >   src_tarball: "{{rpkgname}}_{{version}}.{{extension}}"
           >   vendor_source: "{{baseurl}}/{{rpkgname}}_{{version}}.{{extension}}"
           PKG=knitr
           PKG=RcppArmadillo
           PKG=evaluate
           PKG=highr
           PKG=xfun
           PKG=yaml

     The output confirms that ``Rcpp.yaml`` has changed and shows a different version handling.

#. Update ``set-452.yaml`` and ``versions-452.yaml``

   * ``set-452.yaml``

     The ``buildorder`` entries except two new modules are already in the set file. 
     We established from the check above that the new modules 
     can be added at the end of the set, to be exact to
     the end of the :yvars:`bootstrap1` section keeping the order
     between the two  modules as they are in ``buildorder``. The last few lines
     ``set-452.yaml`` now looks like:

         .. code-block:: yaml

              - qqconf
              - metap
              - mclust
              - scoringRules
            # add non-autogenerated packages, depends on cli, crayon, rappdirs
              - seurat-data

   * ``versions-452.yaml``

     We are going to try first to build the new 2 modules with prerequisites 
     that already exist at the versions we used before.  We append entries only new entries
     for *mclust* and *scoringRules* from ``outversion.yaml`` to the ``versions0452.yaml``.
     The order does not matter.

Add a new set
~~~~~~~~~~~~~

In this second scenario we outline steps to add a new set.
As an example we show how we built a set for R v.4.5.2.

1.  Create a ``set-452.yaml`` with the following contents:

    .. literalinclude:: files/R4-admix-set-new.yaml
       :language: yaml

   This is taken from a trimmed down version of set file for R 4.2.2,
   the latest set we had at a build time.
   It includes just the basic group of packages to build R and rstudio.

#.  Create a ``versions-452.yaml``:

    .. literalinclude:: files/R4-admix-versions-new.yaml
       :language: yaml

    .. attention::  Here the versions numbers for R, GenomeInfoDbData and rstudio come from the
       decision what to install and what is available at a time, and the rest
       of the packages are requirements for building some of the R modules.
       Their version come from building the packages in other admixes. 

#. Use the existing ``modules.desired`` as this provides a basis for what we had 
   for the previous R versions. Likely the same modules will be used by the
   users. This is a perfect time to add any other modules that users have requested. 

#. Download a handful of packages that we need to build initially:

   .. parsed-literal::
      :command:`make download PKG=R SET=452`
      :command:`make download PKG=rstudio SET=452`
      :command:`make download PKG=GenomeInfoDbData SET=452`

#. Build the initial set of packages - bootstrap. 

   .. parsed-literal::
      :command:`make bootstrap SET=452`

   This will build and install version 4.5.2  of R and its module and the rest of
   the packages defined so far in the set.

   At this point it is good to check if a new R is working. At a minumim:

   .. parsed-literal::
      :command:`module load R/4.5.2
      R`

   Note, there is a new direcotry ``00STAGE452`` created in ``yamlspecs/``. 
   This is specific to builds for this set. A separation into build directories
   allows us to build sets in parallel and do not overwrite yaml files for
   different sets and to avoid other temporary files creation collosions.

#. Run the command to create the packages dependency file:

   .. parsed-literal::
      :command:`make builddeps.yaml SET=452`
      ( module load R/4.5.2; \
        cat deps.R | R --slave > builddeps.yaml  )
   
   The stdout will indicate what package were processerd and if there are any errors. 
   There is a new file ``builddeps.yaml`` generated by the above. This file
   contains definitions and dependencies among the packages that will be needed to install
   packages that we defined in ``modules.deired`` (desired plus dependencies). 

#. The next step is to create ``buildorder`` file: 

   .. parsed-literal::
      :command:`make buildorder SET=452`
      ./depend.py > buildorder
      INFO: Not writing yaml file for system package MASS

   Note, the *INFO* line.  This means *MASS* is installed as a part of the
   R RPM, no need to create an extra package for it.

   A few files are generated:

     - ``buildorder`` lists in what ordert order packages should be made in relation to each other.
     - ``outversions.yaml`` lists the versions for the packages.
     -  yaml files for all packages.

   .. note::  When ``depend.py`` is run it will check for the presense of
      *NAME.yaml.apend* files and append them to the created NAME.yaml files. 
      The *append* files are already known (from previous versions builds)
      additions to the build process for the respective yaml package file.

#. Update ``set-452.yaml`` and ``versions-452.yaml``:

   * add ``outversion.yaml`` to the ``versions-452.yaml``.
   * add ``buildorder`` entries to the ``sete-452`` in :yvars:`bootstrap1` section

   .. important:: The additions should be per existing formatting in set  and versions files.

#. Download the sources and record the outcome.

   .. parsed-literal::
      :command:`make prep SET=452`

   A successful download should result in placing downloaded file in ``../sources/``. 
   From all the downloaded sources distributions create a single file to
   contain them all. There is a **specific naming convention for this file**:
   ``sources-YYYYMMDD.tar.gz``. A simple way to make this file (make sure ``sources/`` is empty before doing
   this):

   .. parsed-literal::
      :command:`cd ../sources
      tar czvf ../sources-20260130.tar.gz \*.gz
      mv ../sources-20260130.tar.gz .
      cd ..`

   Update  ``versions-452.yaml`` :yvars:`tarsources`  and add the created file info:

   .. code-block:: yaml

      tarsources: "20260130"

#. Create a freeze directory for this new set. This may need to be updated
   later based on the build outcome. Here it is just the initial content.

   .. parsed-literal::
      :command:`make freeze SET=452`

   This command will create a new directory ``freeze-452`` and copy all the
   created yaml files there. This will be used for building the set.

#. Build RPMs for all the set modules:

   .. parsed-literal::
      :command:`rm -rf 00STAGE452`
      :command:`make bootstrap SET=452`

   The ``rm`` command removes the old contents, since new contents will be
   needed as we created a freeze directory for the set and this
   will be used for the build. The ``make bootstarp`` will re-create
   ``00STAGE452`` anew and will make all the needed links. 

   The bootstrap target will build and install all modules listed in the the set
   file in :yvars:`bootstrap0` and :yvars:`bootstrap1`. Since we already built 
   packages listed in :yvars:`bootstrap0`.

   .. note:: We don't need to rebuild already build packages, so temporarily one
      can comment out entries for :yvars:`bootstrap0` in the set file.
      This will give a bit of a speedup as building R itself takes long time. 
      Remember to uncomment after the buidl is done.

   The build will echo on the stdout commands and their outputs.
   It will build and install RPMS for modules **in the order listed listed in the set file**.

   When errors happen, one need to find what exact package created the errors,
   fix them (no single approach here), and restart the build again.
   If the fix was in package yaml file, copy updated yaml file back to the freeze directory. 

   For example, building from ``s2.yaml`` file gave errors about *abseil-cpp* being
   unavailable. The *abseil-cpp* is a C++ code and library. In order to to fix
   the build:

   - create ``abseil-cpp.yaml`` and ``abseil-cpp-module.yaml`` and build and install respective RPMs. 
   - update ``s2.yaml`` file to include dependency on *abseil-cpp*.
   - update ``set-452.yaml`` and ``versions-452.yaml``  files to include *abseil-cpp*

   Rerun the build RPMs untill all are built. 
   This may take a few iterations for a new set. 

   If there are no errors from RPM installation, the package dependencies are
   most likely correct. There are a few instances when a package requires a
   dependency at a *run time*. One can load ``R/4.5.2`` module, start R and
   randomly check loading of the specific R modules. 

#. Update ``packages.yaml`` file with the new set (see existing entries for info).
  
#. Record all the set modifications.

   At the admix repo top directory update the metadata file:

   .. parsed-literal::
      :command:`sha1sum sources/R-4.5.2.tar.gz >> .R4-admix.metadata
      sha1sum sources/rstudio-2026.01.0-392-x86_64-fedora.tar.gz >> .R4-admix.metadata
      sha1sum sources/GenomeInfoDbData_1.2.15.tar.gz >> .R4-admix.metadata
      sha1sum sources/sources-20260130.tar.gz >> .R4-admix.metadata
      sha1sum sources/abseil-cpp-20250814.0.tar.gz >> .R4-admix.metadata`

   Add and commit all set related changes to git: ``freeze-452/`, ``set-452.yaml``,
   ``versions-452.yaml``, ``packages.yaml`, ``.R4-admix.metadata``.

#. Upload new source distro files to your S3 or similar storage. This will be used 
   for subsequent builds.
