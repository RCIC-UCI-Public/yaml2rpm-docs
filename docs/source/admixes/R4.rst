Building
--------

The `R4-admix repository <https://github.com/RCIC-UCI-Public/R4-admix/>`_ 
is used to build multiple versions of R4 and Rstido. 
R4 is relatively complex build and requires local changes to its Makefile to
accomplish multiple builds.

Here is the full process for rebuilding R4 and its associated modules present in the repo:

.. parsed-literal::
   :command:`git clone https://github.com/RCIC-UCI-Public/R4-admix.git
   cd R4-admix
   make buildall-parallel &> buildall.log &`

.. warning:: 
   This process will install RPMs as it builds. You should do this on a 'disposable' build system.

When building packages for R modules we use native R tools 
and modules such as command ``R CMD INSTALL`` or **miniCRAN** module logic to
get packages recursive dependency resolution.

The following sections provide detailed explanation about repo files,
build process, and adding new modules step-by-step.

In yamlspecs/
~~~~~~~~~~~~~

Standard files
^^^^^^^^^^^^^^

When building R4 modules we not only need to build different versions of
R4 itself but also need to have different modules that were requested by the users
in order to support different types of applications.
Such modules trigger its own chain of dependent R4 modules that need to be installed. 

We create a set of modules to install for each version of R. 
While we try to keep the sets contents the same, sometimes it is not possible
as the specific modules dependencies change.
There is a specific order when in the set a module can be built. Some needs to
be build and installed before others can be compiled. Others need their
dependencies only during the module install.
We have to handle such dependencies carefully so that we do not
create circular references during the build.

``packages.yaml`` (required)
  Yaml format, describes specifics of this admix build.

  .. literalinclude:: files/R4-admix-packages.yaml
      :language: yaml

  Most of the variables in this file are standard
  (:yvars:`site`, :yvars:`system`, :yvars:`bootstrap`, :yvars:`build`, :yvars:`manifest`, :yvars:`sets`).
  There are a few new variables in this file that allow us
  to  define a list of system RPMS to be added only when building for a specific OS.

  - :yvars:`bootstrap` - lists two separate bootstrap variables. The
    :yvars:`bootstrap0` is basically defined via :yvars:`basebuild`: R, R-module,
    rstudio, rstudio-module plus a couple other basic R modules. The
    :yvars:`bootstrap0` can be redefined for eash set. 
    The :yvars:`bootstrap1` is defined from the desired modules. 

  - :yvars:`!ifeq "{{site.os_release}},7,icu-devel,libicu-devel"` was
    evaluated to *icu-devel* on OS 7 and to *libicu-devel* on any later OS.
    This gives us flexibility via this logic to use a single line or file
    instead of rewriting them for a different OS.

  - :yvars:`!eval "'libgit2-devel' if {{site.os_release}} == 8 else ''"`
    is similar to :yvars:`!ifeq` statement. Here on OS 8 *libgit2-devel* RPM will be
    added on the build host before any packages are built.

  - :yvars:`bootstrap` and :yvars:`build` - empty, no builds in the base
    set. All builds are in the specific sets.

  - :yvars:`sets` - lists the sets to be built. Here for a set name we use a short hand
    notation of a R version (452 for R 4.5.2, etc).
  - :yvars:`parallel` -  says build all 6 sets in parallel.

Makefile
^^^^^^^^

The ``Makefile`` is specific to R4-admix.

* It includes a generic template via :yvars:`include $(YAML2RPM_HOME)/sys/Makefile` directive
  that provides defaults used for building RPMs;
* Adds targets to override defaults. For example :yvars:`thaw`, :yvars:`copyset`, :yvars:`thawyamls`, :yvars:`thawsources`.
* Adds specific targets used for a :ref:`creation of additional modules <R4_admix_add_modules>`.
  For example :yvars:`prep`, :yvars:`builddeps.yaml`, :yvars:`buildorder`,
  :yvars:`outversions.yaml`, :yvars:`freeze`, :yvars:`cleanset`. 

When executing any target defined in ``Makefile`` **always give it a set name
as an argument**, for example:

  .. parsed-literal::
     :command:`make bootstrap SET=442`
     :command:`make manifest SET=452`

``common.yaml``
  A template that provides a set of variables for build that is used for
  every R module: 

  .. literalinclude:: files/R4-admix-common.yaml
     :language: yaml

  Here we define all the common varialbes that are reused for every package
  and others that can be overwritten (notably :yvars:`requires`) in a given package yaml file when needed.

| ``rstudio.yaml`` 
| ``rstudio-module.yaml``
|   Used to build *Rstudio* and its module.

| ``abseil-cpp.yaml``
| ``abseil-cpp-module.yaml``
|   Used to build *abseil-cpp* and its module, they are prerequisites for *s2* R module.

| ``GenomeInfoDbData.yaml``
| ``seurat-data.yaml``
| ``tmvnsim.yaml``
|   Used to build a few specific R module packages.

``hdf5r.patch``
  Used to patch specific versions of *hdf5* distribution series *1*. Reference to a
  patch is in the respective  ``hdf5r.yaml`` files in *freeze* directories.
  The patch updates *configure.ac* and *m4* files of the source distro.

``hdf5r-1.3.12.patch``
  Used to patch specific versions of *hdf5* distribution series *2*. Reference to a
  patch is in the respective  ``hdf5r.yaml`` files in *freeze* directories.
  This a patch for *hdf5r* adds compiler flags to downgrade errors to
  warnings. This comes from using gcc compiler series v.15 which has much
  stricter checking.

``NAME.yaml.append``
  Any files with this naming schema are created by hand based on what a
  specific module yaml files needs to include for a successful build.
  While we generate nearly all module yaml files automatically, a few have
  specific build needs that are not possible to address programmatically
  just via using CPAN tools, so they are enabled via creating an append file. 
  The append files are created individually based on specific module
  compilation, patching needs or updates to provides/requires.

  For example, an auto-generated file for *hdf5r* module looks like this:

  .. code-block:: yaml 

     !include common.yaml
     ---
     - package: R module hdf5r
       name: hdf5r
       rpkgname: hdf5r
       version: "{{versions.hdf5r}}"
       baseurl: https://cran.r-project.org/src/contrib
       src_tarball: "{{rpkgname}}_{{version}}.{{extension}}"
       vendor_source: "{{baseurl}}/{{rpkgname}}_{{version}}.{{extension}}"
       requires:
         - R_{{Rversion}}
         - R_{{Rversion}}-R6
         - R_{{Rversion}}-bit64
         - R_{{Rversion}}-bit

  However this  does not have patching info, or compiler directives update
  info. Those are coming from ``hdf5r.yaml.append``:

  .. literalinclude:: files/R4-admix-hdf5r.yaml.append
     :language: yaml

  The resulting ``hdf5r.yaml`` file is a concatenation of the two files above
  and can be found in *freeze* directories.

``modules.bootstrap``
  Listing of a few packages for **R** and **rstudio** that are built initially 
  in the :yvars:`bootstrap0` phase. We need to reference this listing a few
  times when building packages for different sets, using a simple file simplifies the tracking.

``modules.desired``
  Listing of R modules (names one per line)  that we want to install. This is a base template that
  was used initially for building modules for each set. Once a set is built
  a (sometimes modified per final build outcome) file is saved in each *freeze* directory.

.. _R4_admix_sets:

Set specific
^^^^^^^^^^^^

The set files and corresponding versions files enable us to create multiple
versions of desired modules for multiple versions of R:

  .. table::
     :class: noscroll-table

     +---------+---------------+-------------------+------------+
     | R       | Set           |  Versions         | Freeze     |
     | version | file          |  file             | directory  |
     +---------+---------------+-------------------+------------+
     | 4.0.4   | set-404.yaml  | versions-404.yaml | freeze-404 |
     |         |               |                   |            |
     | 4.1.2   | set-412.yaml  | versions-412.yaml | freeze-412 |
     |         |               |                   |            |
     | 4.2.2   | set-422.yaml  | versions-422.yaml | freeze-422 |
     |         |               |                   |            |
     | 4.3.3   | set-433.yaml  | versions-433.yaml | freeze-433 |
     |         |               |                   |            |
     | 4.4.2   | set-442.yaml  | versions-442.yaml | freeze-442 |
     |         |               |                   |            |
     | 4.5.2   | set-452.yaml  | versions-452.yaml | freeze-452 |
     +---------+---------------+-------------------+------------+

When we create specific R modules for a given set we try to keep the listing
consistent but this is not always possible. A new version of a given module
may have different prerequisites for a different set and this results in a
different content of the yaml file for a specific module or a slightly
different set of files. This is why after we create the yaml files for sets 
of modules we save them in *freeze* directories, one directory per set so that there is
no conflict.

Any individual set can be built separately, for example:

   .. parsed-literal::
      :command:`make buildall SET=452`

Sets define individual packages for each R version.
For example ``set-452.yaml`` (partial listing):

  .. code-block:: yaml

     !include packages.yaml
     ---
     versions: versions-452.yaml
     bootstrap0:
       - R
       - R-module
       - GenomeInfoDbData
       - rstudio
       - rstudio-module
       - abseil-cpp
       - abseil-cpp-module
     # contents from buildorder
     bootstrap1:
       - BayesCombo
       - cli
       - magrittr
       - Rcpp
       - rlang
       ...

The :yvars:`bootstrap0` entries are basic packages for this set and they must be built
and immediately installed in the listed order. The entries in
:yvars:`bootstrap1` were created via a special process
(:ref:`see below <R4_admix_add_modules>`) and they
too must be built and installed in the listed order.

The versions files define each package version and any additional variables
needed for building. For example, ``versions-452.yaml`` (partial listing):

  .. code-block:: yaml

     !include versions.yaml
     !include site97.yaml
     ---
     R: "4.5.2"
     Rmajor: "4"
     Rminor: "5"
     tarsources: "20260130"
     addonsources:
     rstudio: "2026.01.0.392"
     rstudio_dist: "2026.01.0-392"
     rstudio_os: "rhel9"
     rstudio_site: "electron"
     rstudio_layout: "new"
     abseil_cpp: "20250814.0"
     OpenBLAS: "0.3.31"
     gdal: "3.12.1"
     geos: "3.14.1"
     proj: "9.7.1"
     fftw: "3.3.10"
     glpk: "5.0"
     hdf5: "2.0.0"
     libgit2: "1.8.5"
     GenomeInfoDbData: "1.2.15"
     seurat_data: "0.2.1"
     ## from outversions.yaml
     BayesCombo: "1.0"
     cli: "3.6.5"
     magrittr: "2.0.4"
     Rcpp: "1.1.1"
     ...
     robustbase_subversion: "6"
     robustbase: "0.99"

Variables :yvars:`gdal`, :yvars:`geos`, and similar provide versions of the
dependent software packages (outside of R4-admix) that are needed for
compilation of some R modules. 

Any variable with :yvars:`_subversion` shows a specific portion of the
package version.  Using it allows us to keep a single :yvars:`vendor_source`
line for multiple versions of each package. There is no single naming schema
how developers name their packages or create distro files. 

.. _R4_admix_scripts:

Scripts
^^^^^^^

There are a few scripts that we created to enable specific tasks.
See the scripts files contents in `R4-admix repository <https://github.com/RCIC-UCI-Public/R4-admix/>`_.
All the scripts are specific to R4-admix.

| ``filter-requires-RPostgreSQL.sh``
| ``filter-requires-rstudio.sh``
| ``filter-requires-styler.sh``
|   These bash scripts are used to parse requires during the ``rpmbuild`` run for
    named packages. They remove some third party hard-coded erroneous
    requirements (such as references to /usr/local or system supplied libraries
    at a specific version that does not exist).
    As a result only OS-installed libraries names are left in requires and they satisfy the package needs.

``deps.R``
  This R script reads the files ``modules.desired``  and ``modules.bootstrap`` to generate a single yaml file
  ``builddeps.yaml`` of all R packages dependencies for the desired modules list. It uses the *miniCRAN*
  R module, which does recursive dependency resolution.
  The ``builddeps.yaml`` file can then be processed to determine the build/bootstrap order
  of R RPMs, it can also be used to place dependencies in R module RPMs.

``depend.py``
  This Python script is called from the ``Makefile`` when there is a need to create some new modules
  for the existing groups or add a new group of modules for a new set. This script was used to create 
  all yaml files for the modules in *freeze* directories.

  The script will take as an input created modules dependency ``builddeps.yaml`` and
  bootstrap list  of modules from ``modules.bootstrap``  and create R modules
  yaml files, ``buildorder`` and ``outversions.yaml`` files.

``downloadpkg.py``
  This Python script reads created ``builddeps.yaml`` and downloads listed
  packages sources distributions.

For details how to use these scripts when adding new modules see the following section.
